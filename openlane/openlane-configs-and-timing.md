## Hold Timing Strategy

| Parameter | Value | Role |
|-----------|-------|------|
| PL_RESIZER_HOLD_SLACK_MARGIN | 2.0 | Post-placement hold buffer target (ns above zero) |
| GRT_RESIZER_HOLD_SLACK_MARGIN | 2.0 | Post-global-route hold buffer target |
| GRT_RESIZER_HOLD_MAX_BUFFER_PCT | 80 | Max % of design instances that hold buffers may consume |
| GRT_RESIZER_FIX_HOLD_FIRST | true | Prioritize hold closure over setup |
| CTS_MAX_SLEW | 0.5 | Maximum clock transition — tighter = lower skew = fewer hold violations |

### CTS_MAX_SLEW vs CTS_MAX_TRANSITION

**`CTS_MAX_SLEW`** is the correct OpenLane 2 parameter name. The OpenLane 1
name `CTS_MAX_TRANSITION` is **silently ignored** in OL2 — the parameter is
accepted without error but has no effect. This mismatch caused multiple failed
hardening runs before discovery. Always use `CTS_MAX_SLEW` in OL2 configs.

### Hold margin selection

Hold violations in OpenLane are caused by clock skew — when the launching clock
arrives later than the capturing clock. The resizer fixes this by inserting
delay buffers on the data path. The margin parameter controls how much above
zero the resizer targets.

| Margin | Risk | Notes |
|--------|------|-------|
| 0.5-1.0 ns | Violations likely | Insufficient for designs with CTS skew >1 ns |
| 1.5 ns | Marginal | CTS-introduced skew can undermine pre-route fix |
| **2.0 ns** | **Recommended** | Attacks hold with sufficient budget; proven across PDK versions |
| 2.5+ ns | Routing congestion | Buffer count explodes; DRT cannot converge at typical utilization |

### Buffer percentage trade-off

The `HOLD_MAX_BUFFER_PCT` caps how many hold buffers the resizer can insert
(as a percentage of total instance count). The community default is 20%.

- **20%** (community default): conservative, may leave marginal paths unfixed
- **80%** (this config): aggressive but proven at ≤35% util
- **90%+**: causes routing congestion — DRT fails to converge

## Routing

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| RT_MAX_LAYER | met4 | Top routing metal; met4-only causes GRT congestion on Sky130 |
| GRT_ALLOW_CONGESTION | true | Allows GRT to finish with overflow (non-fatal) |

On Sky130A, met5 is required even for small designs. The limited routing tracks
on met3/met4 are insufficient when hold buffers add wire demand.

## Signoff

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| QUIT_ON_TIMING_VIOLATIONS | false | Produce GDS even with timing warnings for inspection |

Post-route STA checkers report hold/setup/slew/cap violations as warnings or
deferred errors. With this set to false, the flow always produces GDS and
signoff reports, allowing you to evaluate whether violations are acceptable
(e.g., small hold violations in fast-fast corners only).

## SRAM Macro Integration

Macros with hard SRAM instances require additional configuration to handle
PDK-specific power pins, DRC tool quirks, and LVS extraction.

### Power connections

| Parameter | Purpose |
|-----------|---------|
| PDN_MACRO_CONNECTIONS | Maps SRAM power pins (e.g., vccd1/vssd1 on Sky130) to PDN nets (VPWR/VGND) |

Sky130 OpenRAM SRAMs use `vccd1`/`vssd1` power pins, not the standard
`VPWR`/`VGND`. Other PDKs (GF180, ASAP7) have their own pin naming
conventions. The PDN_MACRO_CONNECTIONS regex must match the actual SRAM
instance names in the flattened ODB netlist.

**Important:** ODB instance names use dot-separated flattened hierarchy
(e.g., `u_fft_top.memory_interface_inst.u_fft_mem.u_bank0`), NOT the
slash-separated names from `keep_hierarchy`. Always dump ODB names with
the `dump_macros.py` script to get the correct names for placement and
PDN regex.

### Magic DRC workarounds

| Parameter | Value | Purpose |
|-----------|-------|---------|
| QUIT_ON_MAGIC_DRC | false | SRAM internals trigger false DRC violations |
| MAGIC_CAPTURE_ERRORS | false | Disables heuristic fatal error detection |

OpenRAM hard macros trigger internal DRC violations (e.g., li.3 spacing)
in Magic `drc(full)`. These are inside pre-verified SRAM IP, not in your
logic. KLayout DRC passes clean and is the authoritative check.

### LVS with SRAM

| Parameter | Purpose |
|-----------|---------|
| EXTRA_SPICE_FILES | Transistor-level SRAM netlist for Netgen LVS |

Without the SPICE netlist, Netgen extracts internal transistors from the
SRAM GDS but the Verilog netlist only has the blackbox — causing thousands
of LVS mismatches. The SPICE file provides the expected device-level model.

### SRAM macro files

All four file types must be provided for each SRAM macro used:

| File | Purpose | Config parameter |
|------|---------|-----------------|
| LEF | Abstract physical layout (pins, blockages) | EXTRA_LEFS |
| LIB | Timing/power characterization | EXTRA_LIBS |
| GDS | Full physical layout for DRC/LVS/tapeout | EXTRA_GDS_FILES |
| SPICE | Transistor netlist for LVS | EXTRA_SPICE_FILES |

These are PDK-specific. For Sky130A, they are in:
`$PDK_ROOT/sky130A/libs.ref/sky130_sram_macros/{lef,lib,gds,spice}/`

## Adapting These Configs

### Different PDK

Replace `pdk::sky130A` with `pdk::<your_pdk>`. Key parameters that vary:

- `STD_CELL_LIBRARY`: e.g., `gf180mcu_fd_sc_mcu7t5v0` for GF180
- `RT_MAX_LAYER`: depends on metal stack (e.g., met4 for ASAP7)
- SRAM power pin names: PDK-specific (vccd1/vssd1, VDD/VSS, etc.)
- Hold margin: may need adjustment based on library characterization

### Different clock frequency

Adjust `CLOCK_PERIOD` to match `1000 / frequency_mhz`. Hold margins are
independent of clock period (hold is a min-delay constraint). Setup margins
scale with period — tighter clocks need lower utilization for setup closure.

### Larger designs (>50K gates)

- Reduce `FP_CORE_UTIL` to 25-30% for designs >50K gates
- Consider reducing `HOLD_MAX_BUFFER_PCT` to 50% to limit routing pressure
- Expect longer runtimes (hold repair is single-threaded, scales with endpoint count)

### Hierarchical hardening

For SoCs with multiple large macros, harden each macro independently (as
done here), then integrate at the top level. This avoids monolithic runs
that take >12 hours and are difficult to debug. Each macro produces a GDS +
LEF that can be used as a hard macro in the top-level integration.

## Floorplan diagrams

The generator emits two complementary floorplan artifacts that tell two
different stories — *what we planned* and *what we built*:

1. **`docs/user_project_wrapper_floorplan.svg`** — *planned* floorplan,
   generated at `soc-generator generate` time directly from the in-memory
   placement data. No external tools required. Ships before any hardening
   tool runs, so reviewers can sign off on the planned layout before
   committing to a multi-hour flow. SVG is text → diffs cleanly in PRs.
   GitHub renders it inline in markdown. This is the canonical, tool-
   independent representation and the diagram embedded in the README.

2. **`docs/user_project_wrapper_layout.png`** — *hardened* layout, rendered
   from the actual `gds/user_project_wrapper.gds` after the wrapper finishes
   hardening. Uses sky130A.lyp layer colors to show the real silicon-ready
   layout — the proof-of-completion picture suitable for contest submissions
   and tapeout reviews.

`run-librelane.sh` calls `openlane/user_project_wrapper/render_hardened_layout.py`
automatically after the wrapper hardens (and after `run-librelane.sh all`). It
is non-fatal: if `klayout` is not on `PATH`, or the hardened GDS does not
yet exist, the step is skipped silently.

To re-render the hardened layout standalone:

```bash
klayout -z -nc -rx -r openlane/user_project_wrapper/render_hardened_layout.py
```

The script searches for `sky130A.lyp` under `~/.ciel`, `~/.volare`,
`dependencies/pdks/`, and `/foss/pdks/sky130A/` — covering ChipFoundry CLI,
volare, in-repo PDK installs, and the OpenLane container layout.
